# Record, Replay, Relax: API Testing a Go App with Keploy

You have a Go API. It works. You *should* have tests for it, but writing them by hand means crafting request payloads, asserting on responses, and mocking out the database, which is often more code than the handlers themselves.

In this tutorial you'll let **Keploy** write those tests for you. You'll run a small Gin + MongoDB app, use it like a normal user for a minute, and walk away with a replayable test suite that doesn't even need the database to run.

## What is Keploy?

Keploy is an open-source testing tool that **generates API tests from real traffic**. Instead of writing a test, you *use* your API while Keploy watches. It saves two things:

- **Test cases:** each request that hit your app, plus the response your app sent back.
- **Mocks:** each call your app made to its dependencies (here, MongoDB) and what came back.

Later, Keploy replays those requests against your app and answers the database calls itself using the saved mocks. If your app's response still matches what was recorded, the test passes. If something changed, you get a diff.

<KeployFlow />

### Why this is useful for a Go developer

- **No test code to maintain.** Your handlers can change shape; you just re-record.
- **No test database.** Mocks stand in for MongoDB, so tests are fast and don't depend on local state.
- **No SDK or code changes.** Keploy works at the network level, so your `main.go` stays exactly as it is.
- **Real-world inputs.** The tests use requests you actually sent, not ones you imagined while writing a test.

## Meet the sample app

The quickstart uses a tiny **URL shortener** from Keploy's [samples-go](https://github.com/keploy/samples-go/tree/main/gin-mongo) repository. It's a Gin HTTP server on port `8080` that stores URLs in MongoDB, with two endpoints:

| Method | Path | What it does |
|---|---|---|
| `POST` | `/url` | Takes a long URL, stores it, returns a short code |
| `GET` | `/:param` | Looks up a short code and redirects to the original URL |

That MongoDB dependency is what makes this sample a good first choice: it lets you see Keploy's mocks in action, not just its HTTP recording.

## Record your first tests

<Steps>

<Step title="Start Keploy in record mode">

```bash
keploy record -c "go run main.go handler.go"
```

**Why:** `-c` is the command Keploy uses to start your app. Keploy launches it and hooks into its network traffic, so you don't touch the app's code.

<Step title="Use the app">

With Keploy running, send some requests from another terminal. First, shorten a URL:

```bash
curl --request POST \
  --url http://localhost:8080/url \
  --header 'content-type: application/json' \
  --data '{"url": "https://google.com"}'
```

Then follow the short link, using the code from **your** response:


<Callout type="tip">

Each request you send becomes one test case, so vary them: shorten a couple of different URLs and try a code that doesn't exist. More variety means better coverage.

<Callout type="info" title="Test cases vs. mocks">

A **test case** is what your API received and returned. A **mock** is what your API asked MongoDB and what MongoDB answered. Replay needs both: the first to know what to send and expect, the second to fake the database.

</Callout>

## Replay the tests

<Todo>Confirm the exact replay command for the local (non-Compose) setup. The quickstart page lists a Docker Compose command here; note what actually worked for you.</Todo>

```bash
keploy test -c "go run main.go handler.go" --delay 10
```

**Why `--delay`:** it tells Keploy how many seconds to wait for your app to boot before sending requests. If tests fail with connection errors, increase it.

<Callout type="success" title="Checkpoint">

You don't need MongoDB for this step. Try stopping the `mongo` container first. The tests should still pass, because every database response now comes from the mocks.

</Callout>

## Where to go next

- **Run it in CI.** Commit the `keploy/` folder and run `keploy test` in your pipeline, so every pull request is checked against real recorded traffic.
- **Handle noisy fields.** Timestamps and generated IDs change on every run; Keploy lets you mark fields as noise so they're ignored during comparison.
- **Try another sample.** The [Keploy quickstarts](https://keploy.io/docs/quickstart/samples-gin/) cover other Go frameworks and databases.

## Recap

- Keploy turns **real API traffic** into test cases, and **dependency calls** into mocks.
- `keploy record` captures; `keploy test` replays and compares.
- Mocks mean replay doesn't need the real MongoDB.
- A changed response shows up as a failing test with a diff, with no assertions written by hand.

That's the loop: **record once, replay forever, re-record when the behaviour is meant to change.**
