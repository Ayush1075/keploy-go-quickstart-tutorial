<Hero />

You have a Go API. It works. You *should* have tests for it, but writing them by hand means crafting request payloads, asserting on responses, and mocking out the database, which is often more code than the handlers themselves.

In this tutorial you'll let **Keploy** write those tests for you. You'll run a small Gin + MongoDB app, use it like a normal user for a minute, and walk away with a replayable test suite that doesn't even need the database to run.

<QuickLoop />

<Callout type="info" title="What you'll learn">

- What Keploy records, and why that's enough to build a test
- How to turn real `curl` calls into test cases and MongoDB mocks
- How to replay them with `keploy test`, even with the database switched off
- What it looks like when Keploy catches a breaking change

</Callout>

## What is Keploy?

Keploy is an open-source testing tool that **generates API tests from real traffic**. Instead of writing a test, you *use* your API while Keploy watches. It saves two things:

- **Test cases:** each request that hit your app, plus the response your app sent back.
- **<Term title="Mock" tip="A saved copy of a conversation with a dependency (here, MongoDB). During replay Keploy plays the database's side back from the recording, so the real database isn't needed.">Mocks</Term>:** each call your app made to its dependencies (here, MongoDB) and what came back.

Later, Keploy replays those requests against your app and answers the database calls itself using the saved mocks. If your app's response still matches what was recorded, the test passes. If something changed, you get a diff.

<KeployFlow />

### Why this is useful for a Go developer

- **No test code to maintain.** Your handlers can change shape; you just re-record.
- **No test database.** Mocks stand in for MongoDB, so tests are fast and don't depend on local state.
- **No SDK or code changes.** Keploy works at the network level, so your `main.go` stays exactly as it is.
- **Real-world inputs.** The tests use requests you actually sent, not ones you imagined while writing a test.

<Callout type="tip" title="My a-ha moment">

The API returns a `ts` field, a nanosecond timestamp that's different on *every* call. I assumed that would make every replay fail until I configured something. It didn't: Keploy spotted the field while recording, marked it as <Term title="Noise" tip="Fields that legitimately change on every run, like timestamps or generated IDs. Keploy leaves them out when comparing a replayed response with the recorded one.">noise</Term> in the test file, and ignored it on replay. More on that [below](#look-at-what-keploy-generated).

</Callout>

## Before you start

Keploy captures traffic using Linux kernel features, so it runs on **Linux** or, on Windows, inside **WSL 2**. I did this whole tutorial from an Ubuntu shell in WSL on Windows 11.

| Tool | Why you need it | Check it with | What I used |
|---|---|---|---|
| Linux or WSL 2 | Keploy needs a Linux kernel (5.10+) | `uname -r` | Ubuntu 24.04, kernel 6.6 |
| Go | Builds and runs the sample app | `go version` | 1.27.1 |
| Docker | Runs MongoDB in a container | `docker --version` | 29.2.1 (Docker Desktop) |
| Git | Clones the sample app | `git --version` | 2.43 |

<Callout type="warning" title="Windows users: stay inside WSL">

Run every command in this tutorial from your WSL (Ubuntu) terminal, not PowerShell. I pasted the record command into PowerShell by mistake and got `The token '&&' is not a valid statement separator`. Type `wsl` first; your prompt should change to something like `you@machine:~$`.

If you use Docker Desktop, make sure it's running. It exposes `docker` inside your default WSL distro automatically.

</Callout>

## Meet the sample app

The quickstart uses a tiny **URL shortener** from Keploy's [samples-go](https://github.com/keploy/samples-go/tree/main/gin-mongo) repository. It's a Gin HTTP server on port `8080` that stores URLs in MongoDB. Gin prints its routes on startup:

```text
[GIN-debug] GET    /:param                   --> main.getURL (3 handlers)
[GIN-debug] POST   /url                      --> main.putURL (3 handlers)
[GIN-debug] GET    /verify-email             --> main.verifyEmail (3 handlers)
```

We'll use the first two:

| Method | Path | What it does |
|---|---|---|
| `POST` | `/url` | Takes a long URL, stores it, returns a short link |
| `GET` | `/:param` | Looks up a short code and redirects (`303`) to the original URL |

That MongoDB dependency is what makes this sample a good first choice: it lets you see Keploy's mocks in action, not just its HTTP recording.

<Callout type="info">

The short code is a hash of the URL, not a random value: shortening `https://google.com` always gives `Lhr4BWAi`. That's why the redirect test you'll record keeps working on every replay.

</Callout>

## Set up and run the app

<Steps>

<Step title="Clone the sample">

`samples-go` holds dozens of samples, and a full clone was slow for me. This fetches only the `gin-mongo` folder:

```bash
git clone --depth 1 --filter=blob:none --sparse https://github.com/keploy/samples-go.git
cd samples-go && git sparse-checkout set gin-mongo && cd gin-mongo
go mod download
```

**Why:** `go mod download` fetches the app's Go dependencies up front, so the first `keploy record` doesn't stall on downloads.

</Step>

<Step title="Move the shipped recordings aside">

The repo already contains a `keploy/` folder with someone else's recordings. Rename it so your own run starts clean:

```bash
mv keploy keploy-shipped
```

</Step>

<Step title="Point the app at your local MongoDB">

Open `main.go`. On line 35 the app connects to a host called `mongoDb`, the service name it uses inside Docker Compose. Change it to `localhost`:

```go title="main.go"
client, err := New("localhost:27017", dbName)
```

**Why:** you'll run the Go app directly with `go run`, outside Docker, so it has to reach MongoDB through the port Docker publishes on `localhost`.

</Step>

<Step title="Start MongoDB">

The compose file expects a Docker network called `keploy-network` to already exist. Without it, you get:

```text
network keploy-network declared as external, but could not be found
```

Create the network once, then start only the database:

```bash
docker network create keploy-network
docker compose up -d mongo
```

```text
 Container mongoDB Created
 Container mongoDB Starting
 Container mongoDB Started
```

**Why:** only the database runs in Docker. The Go app runs on your machine, where Keploy can watch it.

</Step>

<Step title="Sanity-check the app without Keploy">

Start the app:

```bash
go run main.go handler.go
```

Then, in a second terminal, shorten a URL:

```bash
curl --request POST \
  --url http://localhost:8080/url \
  --header 'content-type: application/json' \
  --data '{"url": "https://google.com"}'
```

```json
{"ts":1790780912668271014,"url":"http://localhost:8080/Lhr4BWAi"}
```

**Why:** if something's broken at this point, it's not Keploy's fault. Confirming the app works on its own makes any later error much easier to place.

Stop the app with <kbd>Ctrl</kbd>+<kbd>C</kbd>. Keploy will start it for you in the next section. Leave MongoDB running.

</Step>

</Steps>

```

```

<Callout type="info" title="Open-source build vs. full build">

The open-source binary prints a banner listing MongoDB among the extras of Keploy's full (free with an account) build. In my run, the open-source 3.6.82 build recorded and replayed this app's MongoDB traffic without problems. If you hit database-mocking issues on a different setup, the full build is the one to try.

<Callout type="warning" title="Keploy needs root, and sudo forgets your PATH">

Keploy uses <Term title="eBPF" tip="A Linux kernel feature that lets tools safely observe things like network calls from inside the kernel, without changing the application. It's why Keploy needs Linux (or WSL) and root.">eBPF</Term> to watch network traffic, which requires root. But `sudo keploy` fails to find `keploy` (and `go`), because `sudo` swaps in a minimal `PATH`. The fix, which is also what Keploy's install script sets up as an alias, is to carry your `PATH` through:

```bash
sudo -E env PATH="$PATH" keploy --version
```

</Callout>

## Record your first tests

<Steps>

<Step title="Start Keploy in record mode">

From the `gin-mongo` folder:

```bash
sudo -E env PATH="$PATH" keploy record -c "go run main.go handler.go"
```

**Why:** `-c` is the command Keploy uses to start your app. Keploy launches it and hooks into its network traffic, so you don't touch the app's code. On the first run it also creates a `keploy.yml` config file next to your code.

When you see the agent is ready and Gin has printed its routes, Keploy is recording:

```text
🐰 Keploy: ... INFO    Keploy agent is ready to record test cases and mocks.
🐰 Keploy: ... INFO    Starting Application :  {"executing_cmd": "/usr/bin/sh -c go run main.go handler.go"}
[GIN-debug] GET    /:param                   --> main.getURL (3 handlers)
[GIN-debug] POST   /url                      --> main.putURL (3 handlers)
[GIN-debug] GET    /verify-email             --> main.verifyEmail (3 handlers)
🐰 Keploy(agent): ... INFO    Started ingress forwarding      {"orig_port": 8080, "new_port": 43463}
```

</Step>

<Step title="Use the app">

With Keploy running, send requests from a second terminal. Shorten two URLs:

```bash
curl --request POST \
  --url http://localhost:8080/url \
  --header 'content-type: application/json' \
  --data '{"url": "https://google.com"}'
curl --request POST \
  --url http://localhost:8080/url \
  --header 'content-type: application/json' \
  --data '{"url": "https://github.com"}'
```

```json
{"ts":1790781506903043746,"url":"http://localhost:8080/Lhr4BWAi"}
{"ts":1790781506914908121,"url":"http://localhost:8080/4KepjkTT"}
```

Follow a short link, and try one that doesn't exist:

```bash
curl -i http://localhost:8080/Lhr4BWAi
curl -i http://localhost:8080/doesNotExist
```

```text
HTTP/1.1 303 See Other
Location: https://google.com

HTTP/1.1 404 Not Found
{"error":"url not found"}
```

<Callout type="tip" title="Every request becomes a test, including accidental ones">

Before sending these, I ran a quick `curl localhost:8080/url` just to check the app was up. Keploy recorded that too, as `get-url-1.yaml`. Delete any stray test files before replaying (they're owned by root, so use `sudo rm`).

</Callout>

</Step>

<Step title="Stop recording">

Press <kbd>Ctrl</kbd>+<kbd>C</kbd> in the Keploy terminal. Your tests are now saved to disk.

</Step>

</Steps>

## Look at what Keploy generated

```text
keploy/
└── test-set-0/
    ├── mocks.yaml
    └── tests/
        ├── get-doesnotexist-1.yaml
        ├── get-lhr4bwai-1.yaml
        ├── post-url-1.yaml
        └── post-url-2.yaml
```

Each request became one test file, named after its method and path. Here's the first `POST`, trimmed to the important parts:

```yaml title="keploy/test-set-0/tests/post-url-1.yaml" {17-20}
kind: Http
name: post-url-1
spec:
  req:
    method: POST
    url: http://localhost:8080/url
    header:
      Content-Type: application/json
    body: '{"url": "https://google.com"}'
  resp:
    status_code: 200
    header:
      Content-Type: application/json; charset=utf-8
      Date: Wed, 30 Sep 2026 15:18:26 GMT
    body: '{"ts":1790781506903043746,"url":"http://localhost:8080/Lhr4BWAi"}'
  # (trimmed: extra headers, timestamps, protocol fields)
  assertions:
    noise:
      body.ts: []
      header.Date: []
  created: 1790781506
  app_port: 8080
```

Three things worth noticing:

- **`req` / `resp`** is the whole test: send this request, expect this response. No assertion code.
- **`noise`** lists the fields Keploy decided will naturally change between runs: the `ts` timestamp and the `Date` header. They're skipped during comparison. I didn't configure this.
- The full file also includes a ready-to-run **`curl`** command that reproduces the request, which is handy for debugging a failure by hand.

`mocks.yaml` held **10 mocks, all `kind: Mongo`**. It wasn't only the app's queries: the very first mock is the Go driver's connection handshake with the server (`isMaster`). Keploy recorded everything the app said to MongoDB, so on replay it can answer all of it.

<Callout type="info" title="Test cases vs. mocks">

A **test case** is what your API received and returned. A **mock** is what your API asked MongoDB and what MongoDB answered. Replay needs both: the first to know what to send and expect, the second to fake the database.

</Callout>

## Replay the tests

```bash
sudo -E env PATH="$PATH" keploy test -c "go run main.go handler.go" --delay 10
```

**Why `--delay 10`:** Keploy waits 10 seconds for your app to boot before sending the recorded requests. `go run` compiles first, so give it time.

```text
  TESTRUN SUMMARY. For test-set: test-set-0
	Total tests:        4
	Total test passed:  4
	Total test failed:  0
	Time Taken:         15.05 s
```

All four pass, even though the `ts` value in every response was different from the recording.

## Break something on purpose

Tests that always pass don't prove much. Let's make a change that looks harmless: rename the `url` key in the `POST /url` response to `short_url`, on line 98 of `handler.go`:

```go title="handler.go" {3}
c.JSON(http.StatusOK, gin.H{
	"ts":        time.Now().UnixNano(),
	"short_url": "http://localhost:8080/" + id,
})
```

Replay again with the same `keploy test` command. This time Keploy shows exactly what changed, side by side:

```text
Testrun failed for testcase with id: "post-url-1"
# table borders and padding trimmed
EXPECT HEADER                          | ACTUAL HEADER
Content-Length: [65]                   | Content-Length: [71]
EXPECT BODY                            | ACTUAL BODY
{                                      | {
"url": http://localhost:8080/Lhr4BWAi  | "short_url": http://localhost:8080/Lhr4BWAi
}                                      | }

  TESTRUN SUMMARY. For test-set: test-set-0
	Total tests:        4
	Total test passed:  2
	Total test failed:  2
```

### Other common issues

<Accordion type="multiple" className="not-prose my-6 rounded-lg border px-4">
  <AccordionItem value="sudo-path">

## Where to go next

- **Commit your tests.** Keploy drops a `.gitignore` into `keploy/` that excludes only `reports/`, so the tests and mocks are meant to live in your repo next to the code.
- **Run replay in CI.** Because replay doesn't need the real database, `keploy test` can run in a pipeline on every pull request.
- **Explore further.** The [Keploy docs](https://keploy.io/docs/) cover other Go frameworks and databases, plus how to tune which fields count as noise.

## Recap

- Keploy turns **real API traffic** into test cases, and **dependency calls** into mocks.
- `keploy record` captures; `keploy test` replays and compares.
- Fields that change on every call, like timestamps, are detected as **noise** and ignored.
- Mocks mean replay works with the **database switched off**.
- A changed response shows up as a failing test with a clear expected-vs-actual diff, and you never wrote an assertion.

That's the loop: **record once, replay on every change, re-record when the behaviour is meant to change.**
